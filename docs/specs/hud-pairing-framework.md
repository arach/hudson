# HudPairing Framework Design Spec

## Status

Draft spec for the shared Hudson host-to-mobile pairing primitive. This document is a contract only; it contains no implementation code and intentionally leaves app payloads to consuming apps.

## Purpose

HudPairing lets a Hudson desktop session pair with an iOS companion by scanning a QR code, deriving a shared key, and sending authenticated app requests over a small signed-RPC channel.

The primitive is deliberately narrow:

- one host and one guest per pairing session;
- QR-based trust on first use;
- generic signed requests after pairing;
- app-defined routes and payloads above the channel.

HudPairing is not a session manager, app sync engine, WebRTC layer, Bonjour wrapper, or device-to-device mesh.

Route discovery, user route preferences, LAN/Tailscale/managed-relay fallback,
and winning-route persistence belong to the adjacent
[`HudConnection` orchestration layer](./hud-connection-orchestration.md).
Pairing establishes identity and trust; connection orchestration selects a
trusted route without hardcoding any one app's cascade.

## Reference pattern harvested

Talkie and `talkie-companion-poc` provide the reference implementation. The canonical production shape is:

- host transport is plain HTTP over LAN or Tailscale on port `8765`, implemented by a Bun/Elysia Mac server;
- QR payload is JSON with `publicKey`, `hostname`, `port`, and `protocol`, generated on Apple with `CIFilter.qrCodeGenerator()`;
- handshake is ECDH P-256 plus HKDF, using QR scan as TOFU rather than a separate challenge-response;
- post-pairing requests use HMAC-SHA256 with four headers: `X-Device-ID`, `X-Timestamp`, `X-Nonce`, `X-Signature`;
- signature input is `method`, `path+query`, timestamp, nonce, and SHA-256 body hash;
- replay defense is a 30-second timestamp window plus nonce store;
- server keypair is generated once, persisted, and exposed through `GET /pair/info`;
- paired devices are long-lived mutual sessions with 30-day expiry based on `lastSeen` or `pairedAt`;
- pending pairings can be approved/rejected, with auto-approve as a host policy.

Design lesson: lift the generic cryptographic core and registry shape. The only material Hudson-specific design work is transport generalization for web hosts, because browsers cannot bind a local HTTP port.

## Dependencies

HudPairing v1 builds on existing Hudson primitives:

- `HudVault`: host keypair storage, trusted-peer registry, guest private key and paired-host state;
- `HudQRCode`: advertised host QR generation;
- `HudQRScanner`: iOS QR scan entry point;
- `HudPermissionGate`: iOS camera permission before scanning.

HudPairing must not duplicate secret storage, QR rendering, or camera-permission UI.

## Package shape

Equivalent contracts should exist on web/macOS host and iOS guest:

- TypeScript: `hudsonkit/pairing` or package-policy equivalent;
- Apple: Swift module `HudPairing`.

Public nouns:

- `HudPairingHost`
- `HudPairingGuest`
- `HudPairingTransport`
- `HudPairingQRPayload`
- `HudPairingDevice`
- `HudPairingPendingDevice`
- `HudPairingSignedRequest`
- `HudPairingRoute`
- `HudPairingError`
- `HudPairingScanner` on iOS as a SwiftUI convenience wrapper around `HudQRScanner`.

## Protocol constants

Hudson should avoid Talkie-specific HKDF info strings and protocol names while preserving the proven derivation pattern.

Recommended defaults:

- QR `protocol`: app- or framework-scoped string, default `hud-pairing-v1`;
- auth key HKDF info: `hud-pairing-auth-v1` plus optional app namespace;
- encryption key HKDF info, reserved for future encrypted payloads: `hud-pairing-encrypt-v1` plus optional app namespace;
- timestamp tolerance: 30 seconds;
- paired-device expiry: 30 days since `lastSeen`, falling back to `pairedAt`.

Payload encryption is not part of v1 signed requests. The encryption derivation may be carried forward from Talkie but should stay internal/reserved unless an app explicitly opts into encrypted bodies later.

## QR payload schema

Talkie's payload should be generalized by adding an explicit transport discriminator and relay metadata. The payload must remain compact enough for reliable QR scanning.

Required fields:

- `version`: integer, `1` for v1;
- `transport`: `"lan-http" | "ws-relay"`;
- `publicKey`: base64 P-256 host public key, raw/X9.63 form;
- `protocol`: app/framework protocol string, for example `hud-pairing-v1` or `com.example.app.pairing-v1`;
- `hostId`: stable host identifier generated by HudPairing and persisted in HudVault;
- `displayName`: human-readable host name shown to the guest before pairing.

Transport-specific fields:

For `lan-http`:

- `hostname`: LAN, `.local`, or Tailscale hostname/IP;
- `port`: integer;
- `scheme`: `"http" | "https"`, default `http` for local/Tailscale.

For `ws-relay`:

- `relayUrl`: HTTPS/WSS base URL for the relay rendezvous;
- `relaySessionId`: opaque short-lived session id created by the host;
- `expiresAt`: ISO timestamp or epoch seconds for QR/session expiry;
- `capabilities`: optional list such as `signed-request`, `pending-approval`.

Example shape:

```json
{
  "version": 1,
  "transport": "lan-http",
  "publicKey": "BASE64_HOST_PUBLIC_KEY",
  "protocol": "hud-pairing-v1",
  "hostId": "host_...",
  "displayName": "Arachnid MacBook Air",
  "hostname": "arach-macbook-air.tailnet.ts.net",
  "port": 8765,
  "scheme": "http"
}
```

## Host public API

`HudPairingHost` is the desktop-side controller. It can run in a native macOS process, in a local Bun-backed helper, or in a web host that uses a relay transport.

Construction options:

- `appId`: namespace for vault keys, HKDF info, and route ownership;
- `displayName`: shown in QR and pending-device UI;
- `transport`: `HudPairingTransport` instance or descriptor;
- `vault`: HudVault-compatible secure store;
- `protocol`: optional protocol override;
- `autoApprove`: boolean or policy callback; default should be explicit product decision, not hardcoded globally;
- `deviceExpiryDays`: default `30`;
- `logger`: optional structured logger.

Required host methods:

- `start(): Promise<void>` — initialize keypair, transport listener/session, nonce store, and route dispatcher;
- `stop(): Promise<void>` — stop accepting requests and release transport resources;
- `getAdvertisedPayload(): Promise<HudPairingQRPayload>` — return the QR payload for the active transport;
- `getPublicKey(): Promise<string>` — return persisted host public key;
- `listPendingDevices(): Promise<HudPairingPendingDevice[]>`;
- `approveDevice(deviceId): Promise<HudPairingDevice>`;
- `rejectDevice(deviceId): Promise<void>`;
- `listDevices(): Promise<HudPairingDevice[]>`;
- `revokeDevice(deviceId): Promise<void>`;
- `revokeAllDevices(): Promise<number>`;
- `pruneExpiredDevices(): Promise<number>`;
- `registerRoute(path, handler): Unsubscribe` — install app-owned signed-request handler;
- `dispatch(request): Promise<ResponseLike>` — verify, route, and update `lastSeen`.

Built-in host endpoints/routes, independent of transport encoding:

- `GET /pair/info` returns public key and advertised transport metadata;
- `POST /pair` receives `{ deviceId, publicKey, name }` and returns `approved`, `pending_approval`, or rejection;
- `GET /pair/pending` lists pending requests for host UI;
- `POST /pair/:deviceId/approve` approves a pending device;
- `POST /pair/:deviceId/reject` rejects a pending device;
- authenticated app routes are registered by consumers and are not prescribed by HudPairing.

The host owns:

- keypair lifecycle;
- advertised QR payload;
- pending/approved/revoked device registry;
- signed-request verification;
- endpoint dispatch;
- replay protection and clock-skew responses.

The host does not own:

- app-specific route schema;
- host shell chrome;
- user-facing QR placement beyond small reusable primitives.

## Guest public API

`HudPairingGuest` is the iOS-side controller. It scans a QR payload, derives keys, registers with the host, persists state, and signs future requests.

Construction options:

- `appId`: namespace for vault keys and protocol filtering;
- `deviceId`: stable guest id; generated once if absent;
- `deviceName`: default from `UIDevice.current.name`, overrideable;
- `vault`: HudVault-compatible secure store;
- `scanner`: HudQRScanner-compatible dependency;
- `permissionGate`: HudPermissionGate-compatible camera gate;
- `transportFactory`: creates a guest transport from the QR payload;
- `logger`: optional structured logger.

Required guest methods:

- `scanAndPair(options): async throws -> HudPairingDevice` — request camera permission, scan QR, validate payload, pair;
- `pair(payload): async throws -> HudPairingDevice` — non-UI path for a decoded QR payload;
- `restorePairing(hostId?): async throws -> HudPairingSession?` — rebuild signed client from HudVault state;
- `signedRequest(path, body, options?): async throws -> Response` — send an authenticated app request;
- `disconnect()` — stop transient transport resources without deleting pairing;
- `forgetPairing(hostId?)` — delete guest-side vault state;
- `listPairings()` — enumerate persisted paired hosts.

`HudPairingScanner` should be a convenience SwiftUI component that composes HudPermissionGate, HudQRScanner, and caller-provided receipt copy. Talkie's 4-step scan animation and pairing receipt are the UX reference, but copy/content must be supplied by the consuming app.

## Handshake state machine

Host states:

1. `idle` — no active advertisement.
2. `starting` — loading/generating host keypair and starting transport.
3. `advertising` — QR payload is available.
4. `pairingRequested(deviceId)` — guest posted public key and device name.
5. `pendingApproval(deviceId)` — host policy requires user approval.
6. `paired(deviceId)` — host stored the guest public key and can derive request auth keys.
7. `rejected(deviceId)` — pending request was rejected.
8. `expired(deviceId)` — existing device exceeded expiry window.
9. `revoked(deviceId)` — user removed device.
10. `error` — typed failure with recovery advice.

Guest states:

1. `idle` — no scan in progress.
2. `permissionRequired` — camera permission is not yet granted.
3. `scanning` — waiting for QR.
4. `payloadDecoded` — QR JSON parsed and protocol/transport validated.
5. `derivingKeys` — guest creates P-256 keypair and derives shared secret from host public key.
6. `registering` — guest posts `deviceId`, guest public key, and name to `/pair` or relay equivalent.
7. `pendingApproval` — host accepted request but has not approved yet.
8. `paired` — guest persisted host metadata, its private key, and signed-request client state.
9. `connected` — at least one signed request succeeded.
10. `error` — typed failure with recovery advice.

State transitions must be observable so apps can build native UI around them without scraping thrown errors.

## Post-pairing channel

The v1 channel is a generic signed request primitive:

- API: `signedRequest(path, body, options?)`;
- request body: JSON by default, with binary/file bodies out of scope unless an app transport explicitly supports them;
- route ownership: apps register route handlers on the host; HudPairing only verifies and dispatches;
- method: default `POST`, with `GET` allowed for bodyless routes;
- auth headers: `X-Device-ID`, `X-Timestamp`, `X-Nonce`, `X-Signature`;
- signature input: `METHOD\nPATH_WITH_QUERY\nTIMESTAMP\nNONCE\nSHA256_HEX(BODY_BYTES)`;
- signature algorithm: HMAC-SHA256 using HKDF-derived auth key;
- timestamp tolerance: 30 seconds;
- nonce store: host-side expiring set at least as long as timestamp tolerance;
- host result on success: route response plus updated device `lastSeen`;
- host result on stale timestamp: authentication error including `serverTime` so guests can surface clock skew.

All app semantics live above this layer. Examples like Talkie audio or Scout commands are consumers, not part of HudPairing.

## Persistence shape

All secret and trusted-peer state goes through HudVault. Storage keys below are conceptual; implementations may adapt naming to package policy.

Host vault records:

- `pairing.hostKeyPair`: P-256 private/public keypair, generated once per app namespace;
- `pairing.hostId`: stable host id;
- `pairing.devices`: approved devices array or per-device records:
  - `id`
  - `name`
  - `publicKey`
  - `pairedAt`
  - `lastSeen`
  - `expiresAt` or expiry policy version
  - `transportLastSeen` optional diagnostics
  - app-defined `metadata` optional, non-secret;
- `pairing.revokedDeviceIds` optional tombstones if needed for audit;
- pending pairings should normally be memory-only and expire quickly.

Guest vault records:

- `pairing.deviceId`: stable guest id;
- `pairing.hosts[hostId]`:
  - `hostId`
  - `displayName`
  - `protocol`
  - `transport`
  - transport descriptor needed to reconnect (`hostname`/`port`/`scheme` or `relayUrl`/stable relay binding if applicable)
  - `hostPublicKey`
  - guest `privateKey`
  - guest `publicKey`
  - `pairedAt`
  - `lastSuccessfulContactAt`
  - `approvalState`
  - app-defined `metadata` optional, non-secret.

Private keys must not be available to app route handlers. Route handlers receive verified `deviceId` and request payload, not raw keys.

## Transport model

`HudPairingTransport` abstracts how unauthenticated pairing messages and authenticated signed requests move between host and guest.

Common transport operations:

- host: advertise metadata, receive pair request, receive signed request, respond;
- guest: connect from QR payload, post pair request, send signed request;
- both: expose connection diagnostics and typed transport errors.

### `lan-http` transport

This is the Talkie path and should be the v1 macOS/native-host default.

Shape:

- host runs an HTTP server, preferably Bun/Elysia for TypeScript hosts or equivalent native bridge for Swift hosts;
- default port follows Talkie's `8765`, but must be configurable;
- host QR includes `hostname`, `port`, `scheme`, `publicKey`, `protocol`, `transport`;
- Tailscale hostnames are valid and expected;
- no WebSocket, WebRTC, Bonjour, or MultipeerConnectivity in v1.

Adcanvass:

- proven in Talkie;
- simple to debug with curl;
- works offline on LAN/Tailscale;
- lets the same HMAC middleware pattern be lifted nearly verbatim.

Limitations:

- browser-only web hosts cannot bind a listening port;
- local network permissions, firewalls, and DNS can still fail;
- `http` depends on Tailscale/LAN trust for transport privacy, while HMAC provides request authenticity.

### `ws-relay` transport for web hosts

Browser-hosted Hudson apps need a relay/rendezvous variant because a browser tab cannot listen for inbound LAN HTTP. V1 should define the contract and allow one concrete provider to be chosen during implementation.

Proposed model:

1. Web host starts `HudPairingHost` with `transport: "ws-relay"`.
2. Host creates a short-lived relay session over outbound HTTPS/WebSocket.
3. Relay returns `relaySessionId` and `relayUrl` for QR payload.
4. iOS guest scans QR and opens its own outbound WSS connection to the relay session.
5. Relay forwards opaque pairing and signed-request envelopes between host and guest.
6. Host still owns keypair, approval, device registry, HMAC verification, route dispatch, and app responses.
7. Relay never receives private keys and should not be trusted for authentication. It is a mailbox/pipe, not an authority.

Possible relay providers:

- an opt-in Hudson companion service;
- an app-owned relay endpoint;
- a Tailscale Funnel or Cloudflare Tunnel bridge;
- a local native helper that exposes LAN HTTP and lets the browser control it.

Spec position for v1: support the `ws-relay` transport contract and QR schema, but leave the exact hosted relay provider as a human/product decision. Do not build WebRTC P2P for v1.

Relay envelope should include:

- `sessionId`
- `messageId`
- `kind`: `pair-info | pair-request | pair-response | signed-request | signed-response | error`
- `payload`: JSON payload owned by HudPairing
- optional `deadlineMs` and `correlationId`.

The HMAC signature remains over the logical request method/path/body, not over relay framing.

## Security model

HudPairing v1 authenticates the guest to the host after QR-based TOFU:

- QR scan transfers the host public key and transport coordinates;
- guest generates its own P-256 keypair;
- both sides derive the same HMAC auth key from ECDH shared bits through HKDF;
- host stores guest public key only after approval/auto-approval;
- every app request is signed;
- host rejects unknown, expired, revoked, stale, replayed, or badly signed requests.

Threats addressed:

- unauthenticated devices calling host app routes;
- replay within/after the timestamp window;
- relay tampering with signed request body/path;
- casual device replacement after revocation/expiry.

Threats not fully addressed in v1:

- malicious QR replacement before scan;
- compromised relay causing denial of service or traffic analysis;
- local malware reading process memory;
- LAN observer reading unsigned/unencrypted HTTP response bodies when not using TLS/Tailscale;
- multi-factor verification of host identity.

Human-facing UI should make TOFU explicit: the user is pairing with the host named in the QR receipt and should only scan QR codes shown by their own host.

## Error model

Errors should be typed and parallel HudAI-style recoverable surfaces: stable `code`, human-readable `message`, optional `cause`, optional `recovery`, and optional structured `details`.

Recommended error codes:

- `permissionDenied` — camera permission denied/restricted;
- `qrInvalid` — QR is not JSON or missing required fields;
- `unsupportedProtocol` — protocol/version mismatch;
- `unsupportedTransport` — QR transport is unavailable on this platform;
- `transportUnavailable` — host server, relay, network, DNS, or tunnel unavailable;
- `pairingExpired` — QR or relay session expired;
- `pairingRejected` — host rejected request;
- `pairingPendingApproval` — host accepted but requires approval;
- `deviceUnknown` — host has no approved record for the device id;
- `deviceExpired` — 30-day expiry requires re-pair;
- `deviceRevoked` — host revoked device;
- `signatureMissing` — required HMAC headers missing;
- `signatureInvalid` — HMAC mismatch;
- `requestExpired` — timestamp outside tolerance, include `serverTime`;
- `replayDetected` — nonce reused;
- `vaultUnavailable` — keypair or device state cannot be loaded/stored;
- `routeNotFound` — signed request path has no registered handler;
- `handlerFailed` — app route handler threw or returned invalid response.

Errors should preserve enough detail for diagnostics without leaking secrets or expected signatures.

## v1 acceptance criteria

A v1 implementation is complete when:

1. macOS/native host can start `lan-http`, produce a QR payload, receive a guest pair request, approve/reject it, and persist keypair/device registry in HudVault.
2. iOS guest can request camera permission, scan a HudPairing QR, derive keys, register, persist paired-host state, restore after relaunch, and send a signed request.
3. Signed requests use the Talkie-compatible four-header HMAC scheme, 30-second timestamp window, nonce replay protection, and `lastSeen` update.
4. Device expiry and revocation are enforced before route dispatch.
5. Apps can register at least one host route and call it from guest via `signedRequest(path, body)` without HudPairing knowing the app payload schema.
6. QR payload includes `transport` and validates `protocol`/`version` before connecting.
7. Web host has a documented `ws-relay` transport contract and at least a mockable adapter boundary, even if the production relay provider is chosen later.
8. All secrets and trusted peer records go through HudVault; no plaintext ad hoc JSON store is introduced.
9. Typed errors cover QR, permission, transport, approval, vault, auth, replay, expiry, revocation, and route failures.
10. Demo or tests prove a successful pair, rejected pair, expired/revoked device, invalid signature, stale timestamp, and nonce replay.

## Open human-review items

1. **Web relay provider**: choose between Hudson-hosted companion service, app-owned relay, Tailscale Funnel/Cloudflare Tunnel guidance, or native helper bridge. The spec defines the `ws-relay` contract but does not choose the product/provider.
2. **Auto-approve default**: Talkie auto-approves by default. Hudson should decide whether the framework default is auto-approve, explicit approval, or caller-provided policy. Security posture argues for explicit approval unless an app opts in.
3. **Transport privacy**: decide whether `lan-http` may remain plain HTTP on LAN/Tailscale or whether Hudson requires HTTPS/Tailscale-only for shipped demos.
4. **Protocol namespace policy**: decide whether `protocol` should default to framework-wide `hud-pairing-v1` or be mandatory per app to prevent cross-app pairing reuse.
5. **Encrypted payloads**: Talkie already derives an AES-GCM key. v1 only specifies signed requests. Decide whether any first-party app needs optional encrypted bodies in v1.
6. **Multiple pairings per guest**: v1 persistence supports listing hosts, but product flows should confirm whether the first UI should expose one active host or many saved hosts.
